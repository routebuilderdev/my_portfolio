overview: "A full-stack bookmark manager with user accounts, tags, and collections. FastAPI backend with SQLAlchemy, React frontend with TanStack Query. Built entirely with AI assistance."
problem: "Browser bookmarks are flat and unsearchable across devices. A bookmark manager needs user accounts, structured organization (tags, collections), and a clean search experience — which means designing a relational schema and two coherent codebases that agree on the same API."
constraints:
  - "Must support per-user data isolation"
  - "Bookmarks need both tagging and collection organization"
  - "Search must work across titles, URLs, and tags"
  - "API must be documented and consistent between frontend and backend"
  - "Built entirely with AI assistance"
approach: "Designed a blueprint with a full database schema first: User, Bookmark, Tag, and Collection entities with many-to-many relationships. Built the FastAPI backend with SQLAlchemy 2.x and Pydantic v2 schemas, then the React frontend consuming the API through TanStack Query for server state and Zustand for UI state."
keyDecisions:
  - decision: "FastAPI over Express for the backend"
    reasoning: "FastAPI's Pydantic v2 schemas give automatic validation and self-documenting OpenAPI — which the AI tooling can generate clients against and keeps the frontend/backend contract honest."
    alternatives:
      - "Express for a JS-only stack"
      - "Django for batteries-included admin"
  - decision: "SQLAlchemy 2.x + Alembic for the data layer"
    reasoning: "The relational model (many-to-many bookmarks↔tags, bookmarks↔collections) maps naturally to SQLAlchemy. Alembic migrations let the schema evolve without dropping data."
    alternatives:
      - "Tortoise ORM for async simplicity"
      - "Raw SQL with no migration tooling"
  - decision: "Tags AND collections as separate concepts"
    reasoning: "Tags are lightweight, user-created labels; collections are explicit named groupings. Modeling both (rather than collapsing them into one) matches how people actually organize links."
    alternatives:
      - "Tags only, flatten collections into them"
      - "Folders only, hierarchical and rigid"
  - decision: "TanStack Query for server state"
    reasoning: "Bookmark lists need caching, invalidation, and optimistic updates. TanStack Query manages server state declaratively while Zustand handles the little bits of UI state."
    alternatives:
      - "Redux Toolkit for everything"
      - "Plain fetch + useState everywhere"
