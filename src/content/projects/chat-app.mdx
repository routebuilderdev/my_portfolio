problem: "Building a chat app means juggling real-time transport, authentication, and persistent message history simultaneously. Getting the WebSocket connection, message broadcast, and user identity model to work together is where most real-time apps fail."
constraints:
  - "Messages must appear instantly across all connected clients"
  - "Authentication must gate both REST and WebSocket connections"
  - "Message history must persist after reload"
  - "Must handle multiple rooms with isolated message streams"
  - "Built entirely with AI assistance"
approach: "Built a full-stack real-time architecture from a written blueprint: React + Vite SPA on the front, Node + Express + Socket.IO on the back, PostgreSQL with Prisma for persistence. JWT issued over REST, then verified on the WebSocket handshake to attach the authenticated user to each socket."
keyDecisions:
  - decision: "Socket.IO over native WebSockets"
    reasoning: "Socket.IO provides built-in rooms, automatic reconnection, and fallback transports — all things needed for reliable real-time messaging without hand-rolling protocol edge cases."
    alternatives:
      - "Native ws library for lower-level control"
      - "Polling with fetch every few seconds"
  - decision: "JWT verified on the WebSocket handshake"
    reasoning: "The socket connection needs the same identity as the REST session. Passing the JWT during the handshake lets the server attach the user to the socket and gate room membership server-side."
    alternatives:
      - "Anonymous sockets with client-declared usernames"
      - "Redis-based session store shared with REST"
  - decision: "Prisma + PostgreSQL for message history"
    reasoning: "Chat history is relational (messages belong to rooms belong to users). Prisma gives type-safe queries and a clean schema that the AI tooling could generate and iterate on reliably."
    alternatives:
      - "MongoDB for flexible document storage"
      - "In-memory storage with no persistence"
