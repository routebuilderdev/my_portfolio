overview: "Agent fleets fail together. One shared model, one shared context, one bad instruction, and twenty agents get the same task wrong at the same moment — and nobody insures that, because each agent looks like a separate customer with an independent failure. Correlation is parametric cover for correlated agent failure: an LP funds a pool, a buyer pays a premium for a policy, and the policy pays out automatically when enough agents fail the same task inside a window. The trigger is not an oracle's opinion — it is a proof the contract computes itself."
problem: "Insurance prices independent risk. AI agents don't fail independently: they share prompts, context, tools and models, so a single bad instruction can move a whole fleet at once. The loss is real but invisible to a normal underwriter, and any human-in-the-loop assessment reintroduces the trust problem the product exists to remove. If a payout depends on someone's judgement, the buyer is back to arguing with a claims department."
constraints:
  - "The payout trigger must be verifiable by a third party, not asserted by the operator"
  - "Every agent receipt is ECDSA-signed inside the model's TEE — the contract sees raw request and response bytes only"
  - "Verification must be cheap enough to run per receipt, with finality in seconds"
  - "One hackathon submission per repository — the public artifact had to be finished and honest"
approach: "The build is a Rust smart contract on NEAR plus a TypeScript monorepo for the fleet harness, the verifier API and the demo UI, implemented by AI agents under my specification. When a claim is submitted, the contract re-derives the expected task input from the policy, rebuilds the exact signed text, recovers the signer from the signature, and recomputes the failure arithmetic itself. Twenty signed receipts produce an index; when the index crosses the policy's threshold, the contract pays. Nothing about the payout is decided off-chain."
keyDecisions:
  - decision: "Verify receipts on-chain instead of trusting a report"
    reasoning: "The product only works if the buyer doesn't have to believe the seller. Recovering the signer from the receipt bytes and recomputing the index inside the contract makes the payout a proof rather than a claim. The alternative — an operator-submitted failure report — is exactly the model the product is trying to replace."
    alternatives:
      - "Operator-submitted failure report with on-chain settlement"
      - "Optimistic oracle with a challenge window"
  - decision: "Parametric trigger on an index, not a judgement of harm"
    reasoning: "A policy pays when the measured failure rate crosses a threshold the buyer chose before the run — 2,500 bps in the demonstration. In the recorded run 18 of 20 agents failed (9,000 bps) and the contract paid without anyone approving it. The same fleet on a clean context failed once in twenty (500 bps), which stayed under the trigger."
    alternatives:
      - "Assessed losses after the fact"
      - "Manual claim review with escalation"
  - decision: "Rust contract on NEAR over an EVM chain"
    reasoning: "The workload is many small cryptographic verifications, not a few expensive state writes. NEAR makes each verification cost fractions of a cent and gives finality in seconds, which is what makes per-receipt verification viable instead of a batch job."

      - "Solidity contract with batched verification"

    reasoning: "The contract owner can pause claims, which can delay a payout but cannot redirect one — the payee and amount are fixed when the policy is bought. There is also a known binding gap: a receipt is tied to its policy only through the derived task input, which repeats every 1,000 policy ids. Shipping the demo with those limits written down is cheaper than having a reviewer find them."

## What I'd change now

Two things, both already written into the repository rather than discovered later. The contract owner can pause claims, which delays a payout even though it cannot redirect one — a policy that promises "nobody can stop this" should not have that switch at all. And the receipt-to-policy binding relies on a derived task input that repeats every 1,000 policy ids, so binding the policy id into the signed text is the next contract change, not a paragraph in the release notes.
