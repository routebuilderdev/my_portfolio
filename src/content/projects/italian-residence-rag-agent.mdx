overview: "A production-style retrieval-augmented generation agent for Italian residence-permit questions, rebuilt from scratch as a full-stack .NET application: ASP.NET Core 8 Minimal API with C# 12, a React 18 + Vite chat UI, and an ingestion pipeline that turns PDFs, TXT, and Markdown into confidence-scored, cited answers. A from-scratch .NET port of the Python permesso-bot, designed to be an honest, shippable example of .NET + LLM integration with tests that never touch the network."
problem: "Italian residence permit procedures are complex, multi-step processes with frequent regulation changes, and official information is scattered across PDFs and government websites. The Python proof-of-concept answered the question; the .NET port had to prove the same RAG pipeline could be built as a production-style full-stack application in a different ecosystem — without compromising on verifiability."
constraints:
  - "Must work with local LLMs (Ollama) or hosted OpenAI-compatible APIs — no vendor lock-in"
  - "Answers must carry confidence scores and numbered citations — users must know when to consult a lawyer"
  - "Must use deterministic, offline eval harness — no network calls in the test suite"
  - "Must handle multiple document sources: PDF, TXT, Markdown"
  - "Every shipped line must be understood and reviewable — nothing deploys that I can't explain"
approach: "Designed the RAG engine around a single interface boundary: the OpenAI-compatible HTTP client handles both chat and embeddings, so swapping Ollama for a hosted API is a config change, not a code change. Ingestion uses PdfPig for PDF text extraction with a recursive character chunker (separator ladder with overlap). Retrieval expands the query with immigration-law synonyms (moglie → coniuge, asilo → protezione internazionale), embeds it, and runs top-k cosine search against a vector store behind an IVectorStore abstraction — in-memory by default, Qdrant by configuration. Generation builds a grounded Italian system+user prompt so the model can only answer from context, and confidence is the mean of retrieval scores with per-chunk citation snippets — verifiable, measured, auditable output."
keyDecisions:
  - decision: "From-scratch .NET port over wrapping the Python service"
    reasoning: "Wrapping the existing Python RAG with a thin API would have shipped faster but proved nothing. Rebuilding in ASP.NET Core demonstrated the architecture ports cleanly — engine boundaries, chunking, retrieval, scoring — while forcing the design to survive translation."
    alternatives:
      - "Wrap the Python service behind an API proxy"
      - "Keep the Streamlit UI and add a .NET sidecar"
  - decision: "OpenAI-compatible HTTP client for both chat and embeddings"
    reasoning: "One client, one wire format, zero SDK coupling. Ollama locally, or any hosted provider, by swapping two config keys. The RAG engine never knows where the model runs."
    alternatives:
      - "Vendor SDKs per provider"
      - "Hardcode Ollama's native API"
  - decision: "IVectorStore abstraction — in-memory default, Qdrant switchable"
    reasoning: "A few thousand chunks fit comfortably in memory, so the default is zero-dependency. The Qdrant implementation is already written for production scale — the abstraction is one interface, not a framework."
    alternatives:
      - "Qdrant everywhere from day one"
      - "SQLite vectors only"
  - decision: "Confidence scoring with synonym expansion as the grounding mechanism"
    reasoning: "Legal questions are vocabulary-sensitive: the documents say 'coniuge' while the user asks about 'moglie'. Query expansion closes that gap before retrieval, and confidence — the mean of top-k similarity — plus per-chunk citations makes every answer auditable."
    alternatives:
      - "Raw top-1 retrieval without expansion"
      - "Confidence from the LLM's own estimate"
