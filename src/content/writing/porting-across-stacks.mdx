I already had a working Italian residence-permit assistant in Python — a RAG system with semantic chunking, scenario-aware retrieval, confidence scores, and citations. Users could ask about permit renewals and get grounded answers with sources.

Then I rebuilt it from scratch in ASP.NET Core and C# 12, with a React chat UI. Not because the Python version was broken. Because a rewrite is the cheapest honest exam, and I needed to know how much of what I'd built was *mine*.

## Porting is a map of what you actually understand

When you rewrite a system in a new language, every assumption surfaces. The vector store, the chunker, the retrieval step, the scoring — each one either maps cleanly or dies where it stands.

What survived the translation told me what I understood:
- **The engine boundary.** Chunk → embed → retrieve → generate → score is a pipeline, not a feature list. In Python it lived in loose modules; in C# it became explicit interfaces and typed records.
- **Chunking.** The separator ladder (`\n\n` → `\n` → `.` → space, with overlap) is a real algorithm, not a detail. It ported line-for-line.
- **Confidence as a measured number.** Mean top-k similarity plus per-chunk citations is the same in any language.
- **Synonym expansion.** `moglie` → `coniuge`, `asilo` → `protezione internazionale`. Vocabulary-first retrieval beat prompt-grinding in both stacks.

What didn't survive — because it was scaffolding, not architecture — got a simpler replacement and I did not mourn it.

## Deterministic tests are the honesty instrument

The Python version had tests; the .NET version has *deterministic, offline* tests. A fake embedder (token-hash vectors) and a fake chat completer verify retrieval ordering, citation attachment, no-context fallback, chunking overlap, and synonym expansion — and the suite never touches the network.

That is not a testing detail. It is what makes porting possible in the first place. When you can run the whole decision path in 200 milliseconds with zero network, your loop becomes: port a function, run the tests, see exactly what I broke, move to the next. No local LLM, no Docker, no waiting.

## Rebuilding is cheaper than it sounds — if the first build was honest

The instinct on a working project is to leave it alone. But the second build was dramatically faster than the first — not because I was more skilled, but because the first build's decisions were already *decisions*: recorded, reasoned, and stable. Porting was plumbing; the design work was done and paid for.

That is the strongest argument I found for documenting decisions as you go. The AI partner records *why* at the moment it's decided. When a rewrite comes — and it will — you spend your time at the keyboard, not re-litigating choices from memory. Documentation is velocity, not overhead.

## What I'd carry forward

- **A clean engine boundary ports across a stack change with zero redesign.** Invest there first.
- **One LLM interface (OpenAI-compatible HTTP) keeps the model swappable by config.** The RAG engine never knows where the model runs.
- **Deterministic offline tests are the enabling tool for rewriting.** A network-touching suite makes a port feel like a leap; an offline suite makes it feel like a walk.
- **Confidence + citations are the product**, not the LLM. The model is replaceable; the auditable answer is not.
